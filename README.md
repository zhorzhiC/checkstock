# CheckStock

[![Проверки](https://github.com/zhorzhiC/checkstock/actions/workflows/check.yml/badge.svg)](https://github.com/zhorzhiC/checkstock/actions/workflows/check.yml)

**Где сейчас товар?** Небольшое приложение, которое даёт проверяемый ответ: на каком ФФ он лежит, сколько свободно, что зарезервировано и куда уже отправлено.

Python · FastAPI · PostgreSQL · SQLAlchemy · Alembic · Jinja2

## Запуск за одну команду

Нужен запущенный Docker Desktop с Linux-контейнерами и Docker Compose. Python, Node.js и PostgreSQL на компьютере устанавливать не нужно.

```sh
git clone https://github.com/zhorzhiC/checkstock.git
cd checkstock
docker compose up --build -d --wait
```

Открыть **[localhost:8000](http://localhost:8000)**. Описание API: [localhost:8000/docs](http://localhost:8000/docs). Готовность: [localhost:8000/health](http://localhost:8000/health).

Первый запуск скачивает образы и зависимости. Приложение ждёт готовности БД, применяет миграции и однократно создаёт демонстрационные приходы. Повторный запуск ничего не обнуляет и не дублирует.

```sh
docker compose ps
docker compose logs app
docker compose down
```

`down` останавливает проект; именованный том сохраняет данные. Следующий `up` продолжит работу с теми же остатками. БД не публикует порт на компьютере; веб-приложение слушает только loopback.

Если порт 8000 занят, скопировать `.env.example` в `.env` и поменять `APP_PORT`. Пароль по умолчанию предназначен для локальной демонстрации. При изменении пароля уже созданной БД также потребуется изменить его внутри PostgreSQL; переменная окружения сама существующий пароль не обновляет.

## Что проверить в интерфейсе

| Артикул | Товар | Север | Юг |
|---|---|---:|---:|
| SKU-101 | Органайзер | 10 | 6 |
| SKU-102 | Контейнер | 5 | 0 |
| SKU-103 | Корзина | 0 | 4 |

Всего: 25 шт. на ФФ, 25 доступны, резерв и транзит нулевые. В истории уже видны четыре ненулевых прихода. Товары с нулём на одном из ФФ также присутствуют в таблице.

1. Создать резерв FBS для SKU-101, Север, **12**. Получить отказ: на выбранном ФФ доступно 10, не хватает 2; на Юге есть 6. Числа после отказа не меняются.
2. Нажать предложение переместить **2** с Юга на Север. После отправки: Север 10, Юг 4, между ФФ 2. Эти две единицы ещё недоступны на Севере.
3. В «Отправках и перемещениях» принять перемещение. Север 12, Юг 4. Выбрать «Все статусы» и «Проверить повтор»: второй раз товар не приходуется.
4. Зарезервировать **3** на Севере. Физически 12, резерв 3, доступно 9. Отмена освободит резерв; для продолжения зарезервировать 3 снова.
5. Отправить FBS. Север: физически 9, резерв 0; к клиенту едет 3.
6. Отправить FBO **4** с Юга. Юг 0, в пути FBO 4. Принять FBO: в пути 0, на маркетплейсе 4.
7. Удалить ФФ Север. Он становится архивным; 9 шт. SKU-101 и 5 шт. SKU-102 остаются видны. Доступность действующих ФФ не включает этот склад. Из архива можно вывезти товар перемещением.

Контроль SKU-101: **9 на ФФ + 3 к клиенту + 4 на маркетплейсе = 16**. Для всех товаров после этого сценария: **18 на ФФ + 3 к клиенту + 4 на маркетплейсе = 25**.

Для записи на чистых данных можно запустить отдельный Compose-проект с новым томом, не затрагивая основной:

```powershell
$env:APP_PORT = '8001'
docker compose -p checkstock-video up -d --wait
```

Открыть `http://localhost:8001`. В Bash: `APP_PORT=8001 docker compose -p checkstock-video up -d --wait`.

## Автоматические проверки

```sh
docker compose run --rm app python -m pytest -q
```

Каждый тест создаёт отдельную случайно названную схему **на настоящем PostgreSQL**, применяет настоящую миграцию, выполняет сценарий через HTTP и удаляет только свою схему. Демонстрационные остатки в `public` не меняются. Не запускать этот набор тестов с учётной записью промышленной базы.

Проверяются приходы, резерв/отмена/отправка FBS, оба вида приёмки, нехватка, архивирование с резервом и входящим перемещением, вывоз, имена в истории, изоляция магазинов, валидация и атомарный откат. Отдельные запросы стартуют одновременно через барьер: два резерва последних единиц, одинаковый ключ, двойная приёмка, отправка против отмены. После каждого сценария сверяются позиции, проводки и документы.

CI выполняет те же проверки на PostgreSQL 18 и проверяет синтаксис JavaScript. Подробности ручной приёмки: [docs/acceptance.md](docs/acceptance.md).

## Почему учёт устроен так

### Позиции и журнал — вместе

`positions` хранит текущие количества в местах учёта: конкретный ФФ, межскладской транзит, транзит FBO, транзит FBS, маркетплейс. `documents` хранит состояние бизнес-операции. `events` и `postings` сохраняют неизменяемый журнал и дельты количеств. Они записываются **одной транзакцией**, поэтому обрыв между списанием и приходом не оставит половину операции.

Текущие позиции нужны для простого чтения и проверки доступности. Журнал позволяет пересчитать их независимо. Это обычная транзакционная модель с проводками, без инфраструктуры event sourcing.

На ФФ: `доступно = quantity - reserved`. Резерв входит в физический остаток. При FBS-отправке уменьшаются и физическое количество, и резерв; товар переходит в транзит к клиенту. FBO после приёмки остаётся в учёте на маркетплейсе.

Общий закон сохранения: `приходы = физически на ФФ + между ФФ + транзит FBO + транзит FBS + принято маркетплейсом`. Резерв сюда второй раз не прибавляется. Сверка выполняется также по каждому SKU и сопоставляет резерв/транзит с состояниями документов.

### Конкуренция: сначала корректность

Каждая команда сначала блокирует строку магазина через `SELECT FOR UPDATE`. Внутри короткой транзакции проверяются ключ запроса, склад, доступность и документ, затем записываются проводки. Для одного магазина и малого прототипа это сознательное упрощение: оно закрывает гонки за последними единицами, появление новых позиций и одновременное архивирование без сложной схемы блокировок. Чтения не ждут эту блокировку; снимок экрана читается в `REPEATABLE READ`.

Ограничение — все записи одного магазина выполняются последовательно. При росте нагрузки блокировку можно сузить до магазина/SKU и складов, сохранив общий порядок. Внутри транзакции нет внешних API, загрузок и другой долгой работы.

База дополнительно запрещает отрицательный остаток и резерв сверх физического количества. Триггеры запрещают `UPDATE` и `DELETE` журнала. Это защита от обычных ошибок записи, а не от администратора БД, который способен отключить триггеры.

### Повторы безопасны на двух уровнях

Каждая изменяющая HTTP-команда требует `Idempotency-Key`. Ключ уникален в магазине; рядом сохраняются отпечаток команды и исходный ответ. Повтор с тем же содержимым возвращает исходный результат с `replayed: true`. Изменённое содержимое с тем же ключом получает `409`.

Переход документа дополнительно проверяет его текущее состояние. Повторная приёмка или отправка с **новым** ключом тоже не создаёт проводок. Отправить уже отменённый резерв или отменить отправленный нельзя. Браузер сохраняет ключ при повторе запроса после сетевой ошибки; изменение данных создаёт другой ключ.

### Архив — это место, а не списание

HTTP `DELETE` архивирует ФФ; физических удалений нет. Товар никуда автоматически не перемещается. Свободный остаток архивного ФФ показывается, но исключён из показателя «Доступно к отправке». Разрешены исходящие перемещения и завершение ранее открытых FBS/приёмок. Новые приходы, резервы, FBO и новые перемещения в архив запрещены.

В истории названия маршрута сохраняются на момент создания документа. Переименование фиксируется отдельным событием и не переписывает прошлое. Пустой архив скрывается из таблицы остатков, но остаётся в справочнике и истории.

## API и структура

Все количества — целые штуки от 1 до 1 000 000 на документ. Ошибка возвращается как `{"error":{"code":"…","message":"…"}}`; нехватка дополнительно содержит локальную доступность, дефицит и варианты перемещения.

| Команда | Endpoint |
|---|---|
| Согласованный снимок интерфейса | `GET /api/v1/state` |
| Остатки / документы / история / склады | `GET /api/v1/stock`, `/documents`, `/history`, `/warehouses` |
| Добавить / переименовать / архивировать ФФ | `POST /api/v1/warehouses`, `PATCH/DELETE /api/v1/warehouses/{id}` |
| Приход | `POST /api/v1/receipts` |
| Отправить / принять перемещение | `POST /api/v1/transfers`, `POST /api/v1/transfers/{id}/receive` |
| Резерв / отправка / отмена FBS | `POST /api/v1/fbs-orders`, `POST /api/v1/fbs-orders/{id}/ship`, `/cancel` |
| Отправить / принять FBO | `POST /api/v1/fbo-shipments`, `POST /api/v1/fbo-shipments/{id}/receive` |

`app/inventory.py` — команды и правила; `app/queries.py` — чтение и сверка; `app/main.py` — HTTP; `app/models.py` — хранение; `migrations/` — зафиксированная схема; `app/templates/` и `app/static/` — интерфейс; `tests/` — интеграционные сценарии.

Для разработки без Docker: Python 3.12, `pip install -r requirements.lock`, отдельный PostgreSQL, переменная `DATABASE_URL`, затем `python -m app.start`. БД для этого варианта требуется настроить самостоятельно.

## Границы и развитие

Один демонстрационный магазин, целые штуки, один SKU на документ, полная приёмка. Без возвратов, частичной приёмки, фактического подтверждения доставки FBS и реальных API маркетплейсов. История экрана ограничена последними 200 событиями; база сохраняет все. Интерфейс не делает фоновых изменений: актуализация после команды или кнопкой обновления.

Авторизации нет: это локальное тестовое приложение. `store_id` в модели и фильтрах обеспечивает разделение данных в сервисе, но не заменяет будущую проверку прав. Для промышленного запуска нужны аутентификация, роли, резервные копии, наблюдаемость и нагрузочные проверки.

Перенос расчётов снабжения описан отдельно в [docs/architecture-next.md](docs/architecture-next.md). Сценарий видео и вопросы для защиты: [docs/video-script.md](docs/video-script.md).
