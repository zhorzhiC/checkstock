# CheckStock

Складской учет: приходы, перемещения, FBS и FBO. Стек: Python 3.12, FastAPI, PostgreSQL 18, SQLAlchemy, Alembic, Jinja2.

## 1. Запуск приложения

Нужны Docker Desktop с Linux-контейнерами и Docker Compose. Команда из корня проекта:

```sh
docker compose up --build -d --wait
```

[Приложение](http://localhost:8000) · [Swagger API](http://localhost:8000/docs) · [Проверка готовности](http://localhost:8000/health).

Запуск применяет миграции и однократно создает демоданные: 3 товара, 2 склада, 25 единиц. Данные сохраняются в Docker-томе.
Для изменения порта, пароля БД или заполнения демоданными скопируйте `.env.example` в `.env` и задайте `APP_PORT`, `POSTGRES_PASSWORD`, `DEMO_SEED`.

```sh
docker compose logs app  # логи
docker compose down      # остановка с сохранением данных
```

## 2. Запуск и устройство тестов

После запуска приложения:

```sh
docker compose run --rm app python -m pytest -q
```

Для списка проверок замените `-q` на `-v`. `pytest` проверяет API через FastAPI `TestClient` и реальный PostgreSQL. Каждый тест получает отдельную схему с миграцией и демоданными; после теста схема удаляется. Данные приложения в `public` сохраняются.

Проверяем:

- Приход, резерв, отмену и отправку FBS, отправку и приемку перемещений и FBO.
- Нехватку товара, запрет расхода резерва, неверные данные и недопустимые переходы документов.
- Повторные запросы без двойного учета; конкурентные резервы, приемку, отправку против отмены.
- Создание, переименование и архивирование складов, сохранение истории, изоляцию магазинов.
- Полный откат при сбое, ограничения БД, запрет изменения журнала, совпадение остатков с проводками и документами.
- Демоданные, сквозной сценарий, главную страницу, `/health`, статический JS и схему OpenAPI.

GitHub Actions запускает эти тесты на PostgreSQL 18 и проверяет синтаксис JavaScript.

## 3. Бизнес-логика и учет товаров

ФФ — склад фулфилмента. FBS — отправка клиенту со своего склада; FBO — поставка на склад маркетплейса. Один документ содержит один товар, количество — целое число от 1 до 1 000 000.

На каждом ФФ: `доступно = физический остаток − резерв`. Например, при остатке 10 и резерве 3 доступно 7 шт.

| Операция | Изменение учета |
|---|---|
| Приход | Увеличивает физический остаток выбранного ФФ. |
| Резерв FBS | Увеличивает резерв; физический остаток сохраняется. |
| Отмена FBS | Освобождает резерв. |
| Отправка FBS | Уменьшает остаток и резерв; добавляет товар в путь к клиенту. |
| Перемещение | Списывает свободный товар с ФФ-источника в путь; приемка зачисляет его на ФФ-получатель. |
| Поставка FBO | Списывает свободный товар с ФФ в путь FBO; приемка переводит его в остаток маркетплейса. |

Резерв и товар в пути нельзя расходовать повторно. При нехватке система возвращает дефицит и варианты перемещения с других ФФ.
Архив сохраняет склад, товары и историю. Разрешены вывоз и завершение начатых операций; новые приходы, резервы, входящие перемещения и отправки FBO запрещены.

`positions` хранит остатки и резервы, `documents` — состояние операций, `events` — историю, `postings` — изменения количества и резерва. Все изменения операции сохраняются одной транзакцией; при ошибке откатываются. Триггеры БД запрещают изменение и удаление событий и проводок.

Сверка проверяет каждый товар и общий баланс:

```text
Все приходы = остатки на ФФ (включая архив) + перемещения в пути
            + FBO в пути + FBS в пути + остатки маркетплейса
```

Резерв уже входит в физический остаток. Сверка также сопоставляет остатки с суммой проводок и состояниями документов.

## 4. Логика программы и компонентов

1. `app.start` применяет миграции, добавляет демоданные при `DEMO_SEED=true` и запускает Uvicorn.
2. FastAPI отдает страницу и статику. Браузер получает данные через `GET /api/v1/state`.
3. `app.js` отправляет действие как JSON с `Idempotency-Key`. `main.py` выбирает обработчик, `schemas.py` проверяет поля.
4. `Inventory.execute()` блокирует строку магазина через `SELECT FOR UPDATE`, проверяет ключ запроса и вызывает бизнес-операцию. Изменения одного магазина выполняются последовательно.
5. SQLAlchemy сохраняет результат в PostgreSQL. Интерфейс обновляет данные; `queries.py` читает остатки, документы, историю и сверку в согласованном снимке `REPEATABLE READ`.

Повтор с тем же ключом и данными возвращает сохраненный результат; другой запрос с тем же ключом получает `409`. Повтор завершенного действия по документу не меняет учет, а несовместимое действие отклоняется.
